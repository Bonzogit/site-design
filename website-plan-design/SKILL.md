# 网站策划与设计

把简短的产品或业务需求转成建站执行者能够直接实现的方案。主动完成研究与一般设计决定，不要求用户先交买家画像、完整文案、图库或参考清单。用户只要方案时交付方案；要求建站时把同一方案交给建站 Skill 继续执行。

通用于产品展示、服务获客、品牌内容、交易和工具等网站。网站类型由当前任务决定，不默认外贸询盘站；实际功能由需求和建站能力共同决定。具体项目名称、旧网站布局和过往验收结果不作为新任务默认值。

## 开工判断

先识别当前请求是完善 Skill、制定方案、实施网站还是局部修改。完善 Skill 时维护通用方法，不启动示例网站；仅制定方案时不写业务代码或部署；整体建站才交接后续执行。已有网站的有效内容、功能和用户明确保留的表现是约束，新产品不继承旧站的版式假设。

只给名称时，先建立可修订的工作判断：卖或提供什么、主要访客要完成什么、主要行动是什么、当前真实资料能支持什么。区别“用户给定事实、外部可核实事实、工作假设、待补事实”；猜测不能变成产品参数或企业承诺。资料少也要给出明确推荐与内容草稿，缺项标在受影响位置，不把整份方案退回给用户填写。

## 从需求推导方案

先按[研究能力总入口](references/capabilities.md)识别当前缺口，读取相关方法并检索已整合的能力卡、原始Skill与实验室资料。可用的产品定义、参考、术语、组件和素材能力按任务组合；工具不可用时保留状态，不因为新增资料而套用另一份Skill的固定布局、审批或部署默认。需要核对本包到底用了什么时读[来源与覆盖](references/sources.md)。

1. **确定网站要帮助谁完成什么。** 先识别访客进入时已知什么、要判断什么、行动前担心什么，以及网站期望的主要结果。只有名称时，根据公开资料推导合理的主要访客与用途，标明假设后继续；仅在业务类别都无法判断或目标相互冲突时提问。已有网站先读取当前任务、内容、业务能力和保留项。
2. **从决策障碍安排信息。** 产品研究提取的是选型维度、证据需求、典型疑问和内容差异，不是堆行业常识。按访客需要回答的问题确定页面、导航和阅读顺序；每个模块都要说明“回答什么、依据是什么、为何放这里、下一步是什么”。详读[策划与内容](references/planning.md)，把结论落实到页面蓝图，不能停在“突出优势、提高转化”。
3. **观察参考并做出一套设计选择。** 参考分别解决结构、视觉或交互问题，拟采用的页面需实际观察；来源与观察方式登记。可用时沿用 Refero 的研究方法，资源选择按[资源接入](references/resources.md)，平台不可用仍可使用实际可访问来源。依据产品、内容和素材选一个主方向，明确采用点与舍弃点。按[视觉与交互](references/design.md)落实构图、字体、颜色、密度、图片、组件、状态和响应方式。
4. **把素材与内容变成实施输入。** 输出主要标题、行动文案及关键说明的可用草稿，企业事实与推定分开。图片要指定主体、用途、构图、比例、裁切和来源；需要生成时给出制作要求，不能把概念图当实物证据。长标题、多规格、内容为空、加载失败等困难状态要在方案中有处理方式。缺少非关键资料时选能成立的表达继续，不编造客户、认证、销量、价格或联系方式。
5. **形成可直接建造的交接。** 给出页面蓝图、具体视觉参数、素材清单、关键路径和可观察的验收预期。选取能验证最大设计风险的最小完整样板，可为一页多个状态或跨页；不固定页面数量与模块组合。已有文件就回写同一份方案，按[交接协议](references/handoff.md)连接字段、后台与实现，不让建站执行者重新猜设计。

## 完成条件

涉及已有网站优化、图片浏览、菜单、滚动或动效时，按[体验问题的设计预防](references/experience-prevention.md)补齐保留项、稳定操作区、素材用途与加载/失败、减少动态和相关响应状态。把经验变成本次设计与交接要求，不继承历史站点的配色、列数、时长或版式，也不把旧测试结果当作当前通过证据。

研究到方案的推导按[研究与决策](references/synthesis.md)执行：每个关键决定保留“输入事实/观察 → 判断 → 设计选择 → 实施输入 → 检查预期”。资源不能只列链接，必须说明用在何处、保留什么、为何适配、需要怎样改造。参考冲突时选择主方向，不取平均；装饰、动效和复杂组件没有任务收益就不采用。

交接应足以回答：每页做什么；每块写什么、长什么样、用什么图；访客怎样操作；窄屏与失败状态怎样呈现；内容怎样维护；实际检查什么结果。字体、间距、宽度和裁切给出本次具体选择，不能只写“高级、简洁、响应式”。

交付前用[交接自查](references/readiness.md)找出仍需实现者猜测的关键内容，优先补齐；不以文件数量、检查器通过或参考数量宣称策划合格。方向、关键内容和技术依赖足以开始样板后就交接；不为凑数量继续研究。实现约束影响方案时修订相应决定；验收发现产品逻辑问题返回策划，布局与接线偏差交由建站修复。完整联动见[工作流](references/workflow.md)。

对用户先交代推荐方向与理由、页面和关键模块怎样组织、视觉与素材怎样表达、主要操作怎样完成，以及哪些事实仍待补。实施细节按需展开，不能只汇报“已研究、已生成文档”。需要保存方案时可使用[方案骨架](assets/plan-outline.md)选择实际需要的部分，不强制创建固定数量的文件。

## 与建站 Skill 配合

策划负责网站任务、内容与设计决定；建站负责工程、业务核心、内容保存与部署；验收 Skill 负责对照预期观察实际结果。沿用已有工程和数据，不把参考站或组件库的演示后端带入客户网站。

只有使用 unified-site-builder 时，才读[该建站器的适配规则](references/compatibility.md)并运行对应检查。其他建站器先读取其实际内容、主题和业务接口再映射，不强塞统一建站的文件名与 API。资源脚本默认可检索包内能力卡，按本机配置继续检索规范、实验室和原始研究文件；不能代替设计决定，没有本地资源库仍可使用包内方法与可访问来源完成工作。

换电脑使用[完整迁移包与安装检查](references/portability.md)：方法、已配置资料的完整源码目录、相对路径配置和文件摘要一起迁移。轻量GitHub仓库不含私人完整资源包；不能把只复制SKILL.md描述为资源已迁移。安装后检查实际资料与外部运行依赖，原项目数据和凭据不进入资源包。
