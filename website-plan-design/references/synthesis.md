# 从研究得到设计决定

## 用问题驱动研究

先列会改变页面或设计的未知项，再找证据。常见问题包括：访客按什么维度选择；行动前需确认哪些限制；图片需要解释外观、结构还是使用结果；内容是否适合并排比较；现有后台能保存哪些选项。已知答案不重复调查，纯装饰性问题不拖住关键方案。

每个未知项带着用途检索：`对象或业务 + 访客任务/决策维度` 寻找产品事实；`页面类型 + 内容密度/媒体角色/布局问题` 寻找视觉参考；`实际行为 + 状态/设备约束` 寻找组件与交互。不要把完整产品名称同时当所有库的唯一查询词，也不要仅搜“高级网站”。

专业事实优先原始产品资料、官方手册或可靠一手来源。竞品宣传只能作为其自身表达的观察，不能直接变成当前企业事实。GitHub 项目要读实际文件、许可、入口与依赖；站点参考要看拟采用的页面和状态。无法看到画面时，源码只能支持代码层结论，不能写成视觉观察。

## 为资源分工

| 资源 | 负责解决 | 不据此推断 |
|---|---|---|
| 用户资料、官方产品资料 | 属性、用途、限制、真实业务条件 | 未提供的企业能力、实际客户或商业承诺 |
| 实际网站页面、Refero风格/屏幕/流程 | 构图与视觉、具体界面、操作顺序 | 对当前业务同样有效，或可以复制品牌素材 |
| 规范库与历史分析 | 快速发现表达方式、实现约束和候选来源 | 原站当前画面、当前动画表现或素材授权已核验 |
| 动效与组件库 | 选定交互的实现路径、生命周期、回退方式 | 组件演示的数据接口适合客户后台 |
| 图像工具、可用图库与字体来源 | 具体素材、构图与统一视觉 | 生成内容等同真实产品、工厂、证书或客户证据 |

按[资源接入](resources.md)检索候选后，采用项回读原始内容。先判断相关性，再判断技术可用性与授权；缺项保留未知。每个实际采用项记录具体来源/文件、版本或访问时间、观察方式、负责模块、保留特征、改造点、依赖与替代。没有采用的候选不包装成设计来源。

Refero可用时用样式确定方向、屏幕补充局部模式、流程支持多步任务；不需要的层不硬凑。不可用时记录具体失败，使用可访问页面与可用方法继续；不反复重试相同失败，也不宣称使用过未调用的工具。

## 建立决定链

关键决定用以下关系解释，不必为每个像素填写表格：

`事实或观察 → 用户影响 → 选择与理由 → 具体实施输入 → 可观察预期`

- 判断依赖同一组维度且选项确实足够多时，采用对比或筛选；字段、排序和空态随真实内容确定。不能因库里有轮播就把比较内容藏进轮播。
- 用户需要先理解合作范围时，优先把交付与限制讲清，再安排申请动作；不能把所有页都变成重复询盘入口。
- 某种构图依赖清晰主体与特定留白时，先检查可用图片；不能在无法取得图片时保留空洞的大图首屏，仅靠文案声称方向已完成。

这些是推理方式，不是默认页面规则。每次用当前产品与内容重新得出结论。

## 锁定主方向与解决冲突

先明确本次想保留的特征：画布、排版性格、密度、媒体角色、强调色用途、一个具有识别度且服务内容的细节。借用其他来源时指定局部职责，不让其覆盖主方向。颜色、字体、圆角等按来源中的角色使用，不能把装饰色扩散成所有按钮与背景。

约束冲突按实际需求处理：用户明确要求与品牌约束优先；访客任务和可读性约束表现；素材与实现能力约束具体手法。提出满足目的的替代，说明牺牲的特征，而不是悄悄换成另一套默认主题。两个方向均可行时自主推荐一个，并用任务适配、真实内容、素材可得与维护成本解释舍弃项。

## 何时停止研究

主要任务、页面职责、关键内容、主视觉、核心交互已有足够依据，且剩余缺项不改变关键结构，就进入方案交接。仍不知道核心选型维度或主要操作怎样完成时继续解决相关问题；不以继续收藏网站替代决定。

后补研究标明时间与用途，只能支持后续修订，不能倒写成之前方案的来源。没有独立评审时记录当前执行者自查，不能把多个 Skill 名称写成多人协作。
